# **Architecting Sangrah: A Comprehensive Blueprint for a Cloud-Native, Pay-as-You-Use Storage and Event Platform**

## **Executive Overview and Architectural Strategy**

The paradigm of digital data storage and media sharing has shifted precipitously over the last decade, transitioning from static, on-premise file servers to dynamic, distributed cloud environments.1 However, the commercial models governing these cloud environments have largely stagnated, relying heavily on rigid, subscription-based tiers that charge users fixed monthly fees for arbitrary storage capacities (e.g., paying a flat rate for 100GB regardless of whether the user consumes 1GB or 99GB).2 Concurrently, the social dynamic of sharing media after collaborative events—such as group travel, weddings, or corporate retreats—has devolved into inefficient workarounds.2 Users frequently rely on messaging applications which inherently lack structural organization, compress media destructively, and force users to download massive batches of irrelevant files to their local devices just to locate a few desired images.2

The proposed platform, designated as "Sangrah," is architected to resolve these dual inefficiencies. Sangrah represents a forward-thinking response to the limitations of monolithic architectures by implementing a true "Pay-as-You-Use" billing model, aligning infrastructure costs directly with exact user consumption down to the byte-second.1 Furthermore, the platform introduces collaborative "Events," serving as shared digital galleries with sophisticated Role-Based Access Control (RBAC), machine learning-driven facial recognition for rapid media discovery, and dynamic timeline visualizations.2

To support these advanced capabilities, the underlying architecture must be highly resilient, elastically scalable, and rigorously decoupled.1 The system mandates a microservices architecture implemented via Spring Boot 3, a MongoDB persistence layer optimized for semi-structured metadata and vector search, an event-driven asynchronous processing pipeline utilizing RabbitMQ, and a high-performance Angular frontend.1 This document serves as the exhaustive technical specification and architectural blueprint for the Sangrah platform, adhering strictly to the 12-Factor App methodology, SOLID design principles, and Clean Architecture standards to ensure a production-grade, maintainable, and highly observable distributed system.3

## **Distributed Systems Architecture and The 12-Factor App Methodology**

To achieve the elasticity required for processing highly variable workloads—such as massive spikes in media uploads following a major holiday or social event—Sangrah is designed as a suite of independent, loosely coupled microservices.1 This architectural paradigm explicitly isolates domain functionalities, ensuring that an outage in the Python-based AI inference engine does not compromise the ability of the Spring Boot billing engine to calculate daily costs, nor does it affect the media service's ability to serve file downloads to users.1

### **Strict Adherence to the 12-Factor App Methodology**

The microservices architecture is strictly governed by the 12-Factor App methodology, a set of principles designed to ensure that applications are inherently cloud-native, portable, and resilient against software erosion over time.5 The implementation of these twelve factors within the Sangrah ecosystem is detailed in the following matrix.

| Factor | Principle | Sangrah Implementation Strategy |
| :---- | :---- | :---- |
| **I. Codebase** | One codebase tracked in revision control, many deploys.11 | Each microservice (Auth, Media, Billing, etc.) resides in its own Git repository, utilizing trunk-based development. The same codebase is compiled once and deployed across development, staging, and production environments.4 |
| **II. Dependencies** | Explicitly declare and isolate dependencies.11 | The Spring Boot services utilize Maven pom.xml files to declare exact versions of libraries. ### **Microservice Decomposition and Bounded Contexts**

The domain is decomposed into logically isolated bounded contexts, minimizing synchronous HTTP coupling where possible to enhance fault tolerance.1 The API Gateway, implemented via Spring Cloud Gateway, acts as the unified entry point for all Angular frontend traffic, managing dynamic routing, SSL termination, and rate limiting.1

The Auth Service assumes responsibility for identity management, issuing JWTs, and enforcing Role-Based Access Control (RBAC).1 Because cryptographic hashing (e.g., BCrypt) is CPU-bound, isolating this service allows it to scale independently during authentication storms.1 The Media Service handles file metadata, hierarchical folder logic, and AWS S3 interactions.1 As an I/O-bound service, its performance depends heavily on database and network throughput.1

The Event Service manages the collaborative spaces, tracking user permissions, shared galleries, and dynamic access codes.1 The AI Inference Service, uniquely written in Python using FastAPI and PyTorch, offloads computer vision tasks such as face detection and vector embedding generation.1 This polyglot architectural decision is justified by the superior performance of the Python ecosystem for GPU-intensive machine learning workloads.1 Finally, the Billing Service encapsulates the intricate usage metering, daily cost calculations, and invoicing operations, utilizing Spring Batch to handle massive data volumes during scheduled burst compute windows.1

To mitigate the inherent fallacies of distributed computing, the system utilizes Resilience4j to implement the Circuit Breaker pattern.1 If the AI Service experiences a degradation in processing speed or becomes entirely unresponsive, the circuit breaker opens, allowing the Media Service to immediately return a fallback response (indicating that media is currently processing) rather than blocking threads, exhausting connection pools, and causing cascading system failures.1 Furthermore, distributed transactions that span multiple domains—such as provisioning a new user account and subsequently initializing their corresponding billing wallet—are handled using the Saga Pattern.1 This pattern manages transactions through a sequence of localized events, ensuring eventual consistency by publishing compensatory rollback events if any step in the distributed chain fails.1

## **Clean Architecture and SOLID Design Principles**

The backend microservices are structured using Clean Architecture and Hexagonal (Ports and Adapters) principles. This architectural approach ensures that the core domain logic remains the focal point of the application, entirely insulated from the volatile lifecycles of external frameworks, user interfaces, and database drivers.3

At the center of the Hexagonal architecture lies the Domain layer, containing the enterprise business rules, entities, aggregates, and value objects.3 In Sangrah, the logic dictating how prorated storage costs are calculated or how RBAC permissions evaluate against user actions resides exclusively here. Surrounding the Domain is the Application layer, which orchestrates use cases by defining inbound and outbound ports (interfaces).18 The outermost layer, the Infrastructure (or Tech Framework) layer, contains the adapters that implement these ports.18 This includes Spring MVC REST controllers, Spring Data MongoDB repositories, and AWS SDK clients.18

This separation of concerns rigorously enforces the SOLID principles. The Single Responsibility Principle dictates that a class should have only one reason to change; thus, the logic for generating a presigned S3 URL is entirely separate from the logic validating a user's upload quota.1 The Open/Closed Principle is achieved through interface-driven design; the system can seamlessly integrate a new storage provider (e.g., Google Cloud Storage) by creating a new adapter implementing the StorageProvider interface, without modifying existing domain services.1 Liskov Substitution ensures that any implementation of this storage interface behaves consistently, while Interface Segregation prevents bloated contracts by splitting interfaces into highly cohesive, specialized units.1 Finally, Dependency Inversion is the cornerstone of the Hexagonal model, ensuring that high-level domain modules never depend on low-level infrastructure modules; both depend on abstractions.3

## **Optimizing the Java Ecosystem: Lombok and MapStruct**

Within the Spring Boot 3 environment, the domain entities represent pure business rules. To streamline development, maximize productivity, and radically reduce boilerplate code, the architecture heavily integrates Project Lombok and MapStruct.19

### **Mitigating Boilerplate with Lombok**

Lombok is utilized as a compile-time annotation processor to abstract away repetitive Java constructs, making the source code significantly more concise and readable while maintaining full functionality in the compiled bytecode.21 The @RequiredArgsConstructor annotation is pervasively employed to automatically generate constructors for all final fields.21 This facilitates constructor-based dependency injection—the widely recommended pattern in the Spring ecosystem—eliminating the need for the intrusive @Autowired annotation.21 This approach ensures that dependencies are immutable, guarantees that a class cannot be instantiated in an invalid state, and vastly simplifies mocking during unit testing.21

For immutable Data Transfer Objects (DTOs), the @Value annotation automatically makes fields private and final, generating getters while preventing state mutation, thereby promoting safer and more predictable data handling across concurrent threads.21 The @Builder annotation provides a fluent, highly readable API for constructing complex objects, which is particularly advantageous when mapping intricate domain models.21

However, the architecture mandates strict governance over Lombok usage to prevent severe performance degradations. The usage of Lombok's @Data annotation is explicitly prohibited on JPA or MongoDB domain entities.22 The @Data annotation automatically generates equals(), hashCode(), and toString() methods that inspect all fields.21 In entities containing bidirectional relationships or lazy-loaded associations, this automatic generation frequently triggers infinite recursion (StackOverflow errors) or unintended database queries (LazyInitialization exceptions).22 Instead, entities must use explicit @Getter and @Setter annotations, and developers must manually implement equals() and hashCode() using only the immutable primary key.22

### **Type-Safe DTO Mapping with MapStruct**

To maintain strict Clean Architecture boundaries, the API layer never exposes domain entities directly to the client. Direct entity exposure introduces severe security vulnerabilities, such as Mass Assignment attacks, and tightly couples the external API contract to the internal database schema, severely limiting the ability to evolve the database independently.1 Instead, Data Transfer Objects (DTOs) are utilized exclusively at the application boundaries to dictate exactly what data is ingested and emitted.23

The translation between Domain Entities and DTOs is handled by MapStruct, a sophisticated compile-time code generator that creates type-safe, performant, and highly maintainable mapper implementations.20 Unlike legacy mapping libraries (such as Dozer or ModelMapper) that rely heavily on Java Reflection API at runtime—incurring significant performance penalties and obfuscating mapping errors—MapStruct generates highly optimized, plain Java code during the Maven build phase.20

This provides absolute type safety, allowing mapping discrepancies (such as unmapped target properties or incompatible data types) to be caught by the Java compiler immediately, rather than surfacing as unpredictable runtime exceptions in production.20 The configuration @Mapper(componentModel \= "spring") instructs MapStruct to annotate the generated implementation with @Component, seamlessly integrating it into the Spring ApplicationContext for easy dependency injection into services.24 Furthermore, MapStruct synergizes flawlessly with Lombok's @Builder pattern, automatically utilizing the generated builder methods to construct target objects efficiently.25

## **Production-Grade Exception Handling and RFC 7807**

Robust, standardized exception handling is a critical non-functional requirement for maintaining a predictable API contract in a distributed microservices ecosystem.26 The architecture categorically avoids the anti-pattern of scattering generic try-catch blocks across controllers, a practice that obscures business logic, promotes code duplication, and inevitably leads to inconsistent error responses returned to the client.26

Instead, Spring Boot 3's advanced @RestControllerAdvice annotation is implemented to centralize error handling globally across the entire microservice.28 When a specific exception is thrown anywhere within the service layer—such as a custom ResourceNotFoundException when querying a deleted image, or an IllegalArgumentException for invalid business logic—the global controller advice intercepts the execution thread before the response reaches the client.26 This elegantly decouples error formatting logic from the core business processes.26

### **Implementing ProblemDetail and Standardization**

Crucially, the Sangrah system abandons custom, ad-hoc error payload wrappers in favor of implementing ProblemDetail, a feature natively integrated into Spring Boot 3 that rigorously adheres to the RFC 7807 specification for "Problem Details for HTTP APIs".29 By enabling the property spring.mvc.problemdetails.enabled=true, the framework standardizes error responses into a machine-readable JSON structure containing standardized fields: type (a URI reference identifying the problem type), title (a short, human-readable summary), status (the HTTP status code), detail (a human-readable explanation specific to the occurrence), and instance (a URI reference identifying the specific occurrence).30

By utilizing ProblemDetail, frontend Angular clients and external API consumers receive highly consistent, structured payloads for all errors, drastically reducing client-side parsing complexity.27 The centralized exception handler is also designed to intercept framework-level exceptions, such as MethodArgumentNotValidException.32 Rather than returning a generic 400 Bad Request, the handler parses the binding results and populates the ProblemDetail payload with a map of field-specific constraint violations, providing granular, actionable feedback to the client regarding exactly which input parameters failed validation.32

Furthermore, the exception handler acts as a security barrier. It ensures that internal stack traces or database SQL exception details are absolutely never leaked to the client, which could provide malicious actors with insights into the system's internal topology.27 Instead, unexpected generic exceptions (Exception.class) are logged securely using the SLF4J logger, while the client receives a sanitized, generic 500 Internal Server Error response.27

## **Telemetry: SLF4J Logging and Distributed Tracing**

In a highly decoupled microservices architecture, diagnosing a failure presents a profound challenge.15 A single user action—such as uploading a photo to a shared event—might originate in the Angular client, pass through the API Gateway, reach the Media Service for storage, trigger an asynchronous event to the Event Service for permission updates, and finally reach the Python AI Service for facial recognition.1 If an error occurs deep within the AI Service, identifying the original user request that triggered the failure is impossible without robust, distributed observability.15

### **Structured Logging and Mapped Diagnostic Context (MDC)**

The platform utilizes SLF4J (Simple Logging Facade for Java) backed by the Logback implementation to handle application-level logging.1 To achieve traceability across network boundaries, Sangrah implements Micrometer Tracing, the modern, vendor-neutral successor to Spring Cloud Sleuth within the Spring Boot 3 ecosystem.35

When a request enters the API Gateway, Micrometer Tracing generates a unique traceId representing the entire transaction lifecycle, along with a spanId representing the specific unit of work within that service.33 Micrometer Tracing automatically injects these identifiers as W3C Trace Context headers into all outgoing HTTP requests and RabbitMQ message broker payloads, ensuring the context propagates downstream to all participating microservices.36 Concurrently, it populates the SLF4J Mapped Diagnostic Context (MDC) with these values for every thread executing the request.33

The logging configuration (logback-spring.xml) is explicitly configured to output structured JSON logs.15 Plain text logs, while readable by humans, are notoriously difficult to parse at scale using regular expressions.33 Structured logging ensures that every log entry is emitted as a valid JSON object, inherently including the traceId, spanId, timestamp, level, and serviceName injected from the MDC.15

These JSON logs are asynchronously shipped to a centralized logging architecture, specifically the ELK Stack (Elasticsearch, Logstash, Kibana) or Grafana Loki.15 When a failure occurs, Site Reliability Engineers (SREs) can simply query the specific traceId within the Kibana or Grafana dashboard.34 The system instantly aggregates and chronologically aligns all logs and metrics across every microservice that participated in the transaction, allowing rapid reconstruction of the event timeline and drastically reducing Mean Time to Resolution (MTTR).34

## **OpenAPI 3.0 Documentation Strategy**

Maintaining accurate, up-to-date API documentation is paramount for enabling seamless collaboration between backend microservice teams and the frontend Angular developers.39 The Sangrah platform standardizes its documentation strategy using the springdoc-openapi library, which automatically integrates Swagger UI with the Spring Boot 3 application context.39

REST Controllers are meticulously annotated using the OpenAPI 3.0 specification. The @Operation annotation is utilized to define the summary and description of the endpoint, while the @ApiResponses annotation clearly enumerates all possible HTTP status codes and their corresponding scenarios (e.g., 200 OK for success, 404 Not Found, 400 Bad Request for validation failures).39 Furthermore, the DTO classes are annotated to specify constraints, default values, and example payloads.20

However, in a microservices topology, forcing developers to access separate Swagger UI endpoints for each individual service (e.g., navigating to port 8081 for Auth docs, 8082 for Media docs) is highly inefficient.42 To resolve this, the Spring Cloud API Gateway is configured to act as an aggregator.42 The Gateway fetches the JSON OpenAPI specifications from all downstream microservices and combines them into a single, unified Swagger UI dashboard.42 This centralized portal allows frontend developers to browse, authenticate, and test API endpoints across the entire Sangrah platform from a single interface, significantly accelerating the development lifecycle.42

## **Pay-as-You-Use Billing Engine and Metering Logic**

The core commercial differentiator of the Sangrah platform is its highly granular utility billing model, shifting away from rigid monthly subscriptions to a system that charges users exclusively for exact infrastructure consumption.2 Implementing precise, metered storage requires a sophisticated engine capable of tracking the exact duration a file occupies the system, moving beyond rudimentary daily snapshots which egregiously fail to account for files uploaded and deleted within the same 24-hour window, leading to revenue leakage.1

### **The Byte-Second Algorithm and Event Sourcing**

The billing logic is driven by an Event Sourcing approach.1 Rather than simply updating a static "current storage size" field in a database, every state change regarding storage—such as FileUploaded, FileDeleted, or FileCopied—is recorded as an immutable, timestamped event in the UsageEvents collection.1

The batch job execution follows a strict Reader-Processor-Writer pattern 44:

* **ItemProcessor**: Executes the core business logic, replaying the events to calculate the exact Byte-Seconds utilized during the 24-hour window. * **ItemWriter**: Aggregates the newly calculated costs and updates the user's UsageBucket document. This specific MongoDB schema pattern is designed to store arrays of daily summaries per billing cycle, optimizing read performance drastically when the system must generate the final monthly invoice.1

### **Invoicing and Grace Period Enforcement**

At the conclusion of the monthly billing cycle, the system generates an itemized invoice.2 A critical requirement is the clear separation of costs incurred from the personal Gallery versus costs incurred from hosting shared Events.2 The business logic strictly enforces a 5-day payment grace period.2

A JobExecutionListener within the Spring Batch framework monitors the billing pipeline.44 If a user fails to remit payment within 5 days of the invoice generation date, an automated, asynchronous cleanup task is triggered.2 This routine executes a permanent, irreversible hard delete.1 It utilizes the StorageProvider interface to eradicate the underlying binary objects from AWS S3, followed immediately by the deletion of all associated metadata from MongoDB, ensuring the platform ceases to absorb infrastructure costs for delinquent accounts.1

## **Data Persistence Strategy and AI Pipeline Integration**

The selection of MongoDB as the primary persistence layer is a strategic architectural decision driven by the polymorphic nature of media metadata and the requirement for high-performance, dynamic read patterns.1 Relational database management systems (RDBMS) demand rigid, tabular schemas that struggle to accommodate the disparate, unstructured metadata associated with different file types (e.g., EXIF GPS data, ISO, and shutter speed for photos versus bitrate, codec, and duration for videos) without resorting to complex, poorly performing Entity-Attribute-Value (EAV) tables.1 MongoDB's BSON document model allows this semi-structured data to be stored natively and queried efficiently.1

### **Advanced MongoDB Schema Patterns**

The schema design prioritizes application access patterns, carefully balancing the need to avoid unbounded document growth (the 16MB BSON limit) against the immense performance benefits of pre-joining data.1

**1\. The Subset and Extended Reference Patterns** The Users collection employs the Subset pattern, embedding frequently accessed profile data (such as display names and avatars) directly within the root document to facilitate rapid authentication checks, while offloading heavy, unbounded lists like login history to separate collections.1 For collaborative events, the Events collection utilizes the Extended Reference pattern.1 Rather than storing only an array of user IDs for collaborators—which would necessitate a costly secondary $lookup (JOIN) query to resolve names and avatars every time the UI renders the participant list—the event document embeds a lightweight sub-document containing the user's ID, display name, and specific RBAC permissions.1 This heavily optimizes the read-centric "Event Details" view, accepting the minor trade-off of write amplification should a user eventually change their display name.1

**2\. The Polymorphic Pattern and Soft Deletion** The Media collection relies on a Polymorphic pattern to differentiate between images and videos within the same collection, allowing dynamic metadata sub-documents based on the type field.1 Furthermore, a Soft Delete pattern is implemented to protect the referential integrity of the "Reference" feature.1 If a user adds an image from their personal gallery to a shared event as a "Reference," deleting the image from their personal gallery merely appends a deletedAt timestamp to the media document rather than executing a hard drop.1 Standard user-facing queries filter out documents containing this timestamp, rendering them invisible in the gallery. However, the Event Service can still resolve the underlying media ID by bypassing the filter, ensuring the shared event timeline is not abruptly broken by an individual's personal gallery action.1

### **Event-Driven Artificial Intelligence Pipeline**

The integration of advanced facial recognition transforms Sangrah from a passive storage locker into an intelligent, semantic media ecosystem.1 Because Python remains the unrivaled industry standard for computer vision frameworks, the architecture bridges the Java backend and the Python AI Inference Service using an asynchronous, event-driven pattern via RabbitMQ.1

When the Media Service successfully finalizes an S3 upload, it publishes a media.uploaded event to a highly available RabbitMQ exchange.1 The Python-based AI Service consumes this queue asynchronously, acting as a critical shock absorber during periods of massive traffic spikes (e.g., users batch-uploading thousands of wedding photos simultaneously).1

The AI pipeline executes a complex, multi-stage computer vision process 1:

1. **Detection**: The service utilizes RetinaFace, a state-of-the-art detection model from the InsightFace library, to locate faces within the image, capable of recognizing subjects even at drastically varying scales or in heavily crowded environments.1  
2. **Alignment**: Affine transformations align the detected faces to a standard frontal geometry using critical facial landmarks (eyes, nose, mouth corners), significantly improving downstream accuracy.1  
3. **Extraction**: The aligned facial crops are processed by the ArcFace Deep Convolutional Neural Network (CNN). This ResNet-100 backbone maps the complex facial features into a 512-dimensional vector embedding, an array of floating-point numbers invariant to lighting and pose changes.1

A decisive advantage of utilizing MongoDB Atlas is its native Vector Search capabilities.1 Traditional architectures would require deploying and synchronizing a separate, dedicated vector database (like Pinecone or Milvus) to handle machine learning embeddings. In Sangrah, these 512-dimensional vectors are stored directly alongside the media metadata in the Media collection.1 An Hierarchical Navigable Small World (HNSW) vector index is configured on this field.1 When a user invokes the "Find My Face" feature, the system executes a $vectorSearch aggregation pipeline utilizing cosine similarity to enable high-speed, approximate nearest neighbor (ANN) queries, retrieving highly correlated media across massive datasets instantly.1

## **Frontend Engineering and Performance Optimization**

Rendering thousands of high-resolution images within a browser Document Object Model (DOM) inherently risks memory exhaustion, severe layout thrashing, and unresponsiveness.1 The Angular frontend is engineered to mitigate these constraints while providing a fluid, native-like user experience.

### **Architectural Structure and Modularity**

The Angular workspace strictly adheres to a feature-based, domain-driven folder structure, ensuring maintainability across large development teams.1

* **Core Module**: Contains singleton services (e.g., AuthService), HTTP interceptors for appending JWTs to outbound requests, global error handlers, and route guards. This module is imported exactly once in the root application and never in feature modules.10  
* **Shared Module**: Houses reusable, "dumb" UI components, common pipes, and directives (e.g., custom masonry layout pipes, standardized action buttons) utilized across various domains.10  
* **Feature Modules**: The application is divided into logical, domain-specific modules such as GalleryModule, EventsModule, and BillingModule.10 Crucially, these modules are lazy-loaded via the Angular Router.1 Lazy loading ensures that the browser only downloads the specific JavaScript bundles necessary for the current route, drastically reducing initial application load times and improving the Time to Interactive (TTI) metric.1

### **Virtual Scrolling and Masonry Rendering**

To support the demanding daily, monthly, and yearly timeline views, the frontend implements sophisticated data virtualization using the Angular Component Development Kit (CDK).1 The VirtualScrollViewport ensures that only the DOM elements currently visible within the user's viewport—plus a minor buffer to ensure smooth scrolling—are actually rendered.1 As the user scrolls through the timeline, DOM nodes that exit the viewport are aggressively recycled and repopulated with new data. This ensures the browser maintains a constant, low memory footprint regardless of whether the gallery contains a hundred or a hundred thousand images.1

Because media files inherently possess variable aspect ratios (portrait, landscape, square), standard fixed-height virtual scrolling logic fails entirely. The system relies on a custom virtual scroll strategy utilizing CSS Flexbox ordering or CSS Columns combined with a bespoke MasonryPipe.1 This pipe distributes images into dynamic vertical columns without horizontal gaps, allowing natural HTML structure stacking without triggering heavy, synchronous JavaScript layout recalculations that would otherwise cause the UI to stutter.1

Bandwidth consumption—a critical factor for mobile users—is minimized using Angular's NgOptimizedImage directive (ngSrc). This directive automatically generates srcset attributes, ensuring mobile devices request appropriately scaled thumbnails from the CDN, while desktop users receive higher-resolution previews.1 It also prioritizes the Largest Contentful Paint (LCP) element, bypassing lazy loading for the first visible image to improve perceived performance, while aggressively lazy-loading off-screen assets.1

## **Security, Privacy, and Regulatory Compliance**

Given the handling of personal media, financial billing data, and sensitive biometric information, Sangrah is engineered to comply with strict global privacy frameworks, most notably the India Digital Personal Data Protection (DPDP) Act of 2023\.46

### **Data Protection, Access Control, and Encryption**

Identity management delegates to robust OAuth2/OIDC standards, utilizing short-lived Access Tokens (JWTs) paired with secure, HttpOnly, Secure-flagged refresh cookies to thoroughly mitigate Cross-Site Scripting (XSS) token theft vulnerabilities.1 All inter-service backend communication across the microservices mesh is secured via Mutual TLS (mTLS), while public frontend traffic strictly terminates over TLS 1.3 at the API Gateway.1

Data at rest within MongoDB Atlas is encrypted at the volume level.1 To ensure compliance with the DPDP Act's rigorous security safeguard mandates, the system enforces granular, instance-level access control.1 Standard role checks (e.g., ROLE\_USER) are insufficient for managing shared events. Instead, custom Spring Security PermissionEvaluator classes dynamically assess whether a user holds the necessary specific rights (e.g., UPLOAD\_MEDIA, DELETE\_EVENT, VIEW\_PROTECTED) on a particular document instance before granting the thread execution rights.1

### **Biometric Compliance and Data Principal Rights**

The extraction, storage, and processing of facial embeddings represent the handling of sensitive biometric data. Under the DPDP Act, organizations (Data Fiduciaries) must ensure purpose limitation, obtain explicit and verifiable consent via localized Consent Managers, and immediately facilitate the Data Principal's absolute right to erasure.46 Non-compliance with these security safeguards can result in catastrophic financial penalties, scaling up to ₹250 crore.46

To support privacy by design, the FaceEmbeddings collection is strictly anonymized; it maps high-dimensional vectors to an arbitrary, system-generated personId rather than linking directly to Personally Identifiable Information (PII) such as a user's name or email.1

If a user invokes their Right to be Forgotten—a core provision of the DPDP Act—or if their account is terminated due to billing delinquency, the backend microservices execute a cascading hard delete.1 This distributed operation permanently purges the vector embeddings from the index, removes all metadata from MongoDB, and issues a destructive delete command to the AWS S3 buckets.1 The original binary files and all mathematical representations of the user's biometrics are eradicated from the system, ensuring absolute regulatory adherence, mitigating legal exposure, and preventing residual data leakage.1

## **Strategic Synthesis**

The architecture of the Sangrah platform represents a rigorous alignment of innovative business utility with highly advanced distributed systems engineering. By proactively discarding the legacy monolithic paradigm in favor of Spring Boot 3 microservices mapped precisely to bounded contexts, the system achieves the elasticity required for processing highly unpredictable media workloads and compute-intensive artificial intelligence tasks.

The strategic implementation of Clean Architecture, leveraging the power of MapStruct and Lombok, ensures highly maintainable, type-safe, and boilerplate-free code that remains entirely decoupled from infrastructure nuances. The persistence layer's reliance on MongoDB provides the critical schema flexibility necessary for polymorphic media metadata, while simultaneously enabling native, high-speed vector search for semantic facial discovery. Furthermore, the event-driven RabbitMQ pipeline guarantees that heavy AI inferences act asynchronously, ensuring they never impede the critical path of the user experience.

Ultimately, the core innovation—the granular, pay-as-you-use billing engine—is realized through precision engineering utilizing Spring Batch and the byte-second metering algorithm. Supported by a highly optimized, modular Angular frontend capable of rendering massive datasets without performance degradation, Sangrah provides a definitive blueprint for a highly resilient, cloud-native utility platform that is scalable, secure, fully compliant with modern data protection regulations, and commercially viable for the modern digital era.
